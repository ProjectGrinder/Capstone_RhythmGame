    \begin{abstract}
        The Entity-Component-System (ECS) pattern is used for applications in interactive systems,
        machine learning, and digital simulation contexts.
        From examining existing infrastructure and tools, such as EnTT, Bevy Engine, and the Unity Data-Oriented Technology Stack (DOTS), and comparing to theoretical models,
        we identified opportunities to reduce ECS runtime overhead and increase performance through increased compile-time specialization.
        We present an ECS framework built upon C++ that aggressively applies compile-time
        metaprogramming techniques to reduce overhead to analyze the potential of this approach.
        The framework was evaluated in comparison with EnTT
        and Bevy ECS in terms of performance, executable size, and memory usage.
        The results showed that our framework performs similarly compared to existing frameworks while
        improving program size at a small cost to memory usage in tested workloads.
    \end{abstract}

    \section{Introduction}
    \label{sec:introduction}
    Entity-component-system (ECS) is a data-oriented software architectural pattern widely used in interactive systems, simulations, and machine learning.
    An ECS represents entities through collections of data-oriented components, with systems defining the behavior that operates on those components.
    An entity's behavior therefore emerges from the systems that add, remove, or modify its components.

    ECS has been adopted in several production frameworks, including EnTT~\cite{ValtoLibraries_EnTT}, a header-only C++ library used in projects such as the Bedrock edition of Minecraft~\cite{mojang_minecraft_attribution},
    and Bevy ECS~\cite{Bevy_Engine}, a Rust-based ECS used, for example, in~\cite{machine-learning-bevy}.

    Existing ECS implementations have different trade-offs between runtime flexibility and compile-time optimization.
    While templates and generics are commonly used to specialize frequently executed operations,
    other parts of an ECS may rely on runtime registration, type erasure, or dynamic scheduling to be more flexible and extendable.
    Compile-time specialization is typically applied selectively rather than throughout the ECS architecture.

    This work investigates the extent to which ECS functionality can be specialized at compile time.
    We develop a custom ECS framework designed to maximize compile-time specialization while retaining an
    interface suitable for practical software development.
    We then evaluate its performance against existing production ECS frameworks through a set of benchmarks.

    \section{Related Work}
    \label{sec:related-work}

    Several established ECS frameworks employ static techniques to reduce runtime overhead, but they differ in how
    extensively they rely on compile-time specialization.

    EnTT uses C++ templates and metaprogramming extensively.
    Component views, registries, and queries are represented by template types, allowing the compiler
    to generate specialized implementations for particular component combinations.
    This enables optimizations such as function inlining and dead-code elimination while avoiding forms of runtime dispatch.

    Bevy ECS similarly relies on Rust's generic type system and monomorphism.
    Systems express their component accesses through generic query types, from which the compiler generates specialized code.
    Rust's ownership and borrowing system additionally provides compile-time guarantees concerning aliasing and mutability,
    enabling further optimization of memory accesses while retaining strong safety guarantees.

    Unity's Data-Oriented Technology Stack (DOTS)~\cite{Unity_DOTS} takes a more explicit code-generation approach.
    Its Entities package~\cite{unity_entities} uses C\# source generators to produce specialized code for entity queries,
    which is subsequently optimized by the Burst compiler.
    DOTS also performs static analysis of system dependencies to construct execution schedules,
    reducing runtime scheduling overhead.

    These frameworks demonstrate several established approaches to compile-time optimization in ECS,
    but they differ in which parts of the architecture are specialized statically and which remain dynamic.
    This work builds on these approaches by investigating a more comprehensive application of compile-time specialization across ECS functionality.

    \section{Design}
    \label{sec:design}

    The primary design goal of the custom ECS was to investigate how extensively ECS functionality can be specialized at compile time.
    To this end, we applied static typing and template-based specialization across component storage, system registration, and query construction.
    The resulting framework was designed to retain a conventional ECS programming interface while moving as much type-dependent work as possible from runtime to compile time.

    The framework was implemented in C++20, for it provided the language features required for this approach.
    This included templates, concepts, compile-time evaluation, and type deduction, while also providing direct control over memory layout and storage.
    These features allowed component types and system interfaces to be represented natively within the framework.

    \subsection{Compile-Time Specialization}\label{subsec:compile-time-specialization}

    The implementation applies compile-time specialization in three main areas:

    \begin{itemize}
        \item \textbf{Component Storage.} Component types are represented directly in the storage types used by the ECS\@.
        The framework derives the storage information at compile time, allowing component access to be expressed through statically known types.

        \item \textbf{System Registration.} Systems are represented by their function types.
        C++ concepts (compile-time predicates) are used to constrain the functions that may be registered as systems, while function-trait mechanisms extract the component types accessed by each system.
        This information is used to validate system requirements during compilation.
        For example, systems that use components not registered with the framework would emit an error at compile-time.
        Systems are stored in a compile-time structure and invoked according to their registration order, allowing the compiler to generate for registered systems the appropriate parameters and execution order.

        \item \textbf{Query Construction.} Query component types are specified as C++ template parameters, allowing the compiler to generate specific query types as needed by systems.
        The framework uses parameter packs and compile-time expansion to construct the component accesses required by a query, such that the implementation can generate access operations specialized to the query's component set.
    \end{itemize}

    These mechanisms define the main distinction between the custom framework and the more dynamic portions of existing ECS implementations.
    The goal of the specialization is to determine and remove as much type-dependent ECS work from runtime to compilation while keeping the framework interface lean and simple to use.
    Runtime overhead for certain mechanisms in the framework remained essential, such as in entity organization and providing query references to systems.
    \subsection{Component Storage}\label{subsec:component-storage}

    A crucial decision we had to make was choosing the type of component storage because it directly affects the performance of entity iteration and modification.
    Two common approaches are archetype-based storage and sparse-set-based storage.
    Archetype storage organizes entities based on the component set attached to them, providing efficient iteration over entities with the same component group.
    Sparse-set storage instead maintains a dense component array with an indexing structure, allowing for efficient component lifecycle management.
    These approaches therefore represent trade-offs between iteration and structural modification costs. \cite{cox2025run}

    We selected sparse-set storage as they provide a relatively direct mapping between a component type and its storage,
    making them suitable for isolating the effects of compile-time specialization in component access and query construction.
    Outside of this, however, the choice of storage also proves a useful comparison point with existing ECS implementations.
    In particular, EnTT uses sparse-set storage, while Bevy defaults to archetype-based storage but provides both types depending on configuration.

    \section{Evaluation}
    \label{sec:method}

    For each framework, final executable size was measured using the device's File Explorer,
    while memory usage was recorded from the Memory column in the device's Task Manager during steady-state benchmark execution.

    Execution time was measured as the interval encompassing all user-defined systems within a frame.
    Bevy used Rust's \verb|Instant|~\cite{rust_instant}, while EnTT and our implementation used C++ \verb|std::chrono::steady_clock|~\cite{cpp_steady_clock}.
    Rendering, unrelated plugins, and other external factors were excluded to isolate ECS execution time.

    Four benchmark scenarios evaluated the frameworks under different workloads.
    In each scenario, user-defined systems performed equivalent work across implementations.
    Entity creation and destruction benchmarks maintained a steady-state workload by restoring the ECS world to an equivalent state after each frame.

    Each benchmark was warmed up before measurement, after which execution time was recorded for 1,000 consecutive frames and logged.
    The samples were then averaged to obtain the mean execution time for each configuration.

    All benchmarks used release optimizations: Bevy was built with \verb|cargo --release|, while the C++ implementations used the MSVC Release configuration with Clang.
    Tests were conducted on local hardware using the same machine and operating environment to ensure consistency across measurements.

    The hardware specifications are as follows:
    \begin{itemize}
        \item CPU: 11th Gen Intel(R) Core(TM) i7-11800H @ 2.30 GHz
        \item GPU: Intel(R) UHD Graphics
        \item Memory: 3200 MHz 16.0 GB RAM
        \item Operating System: Windows 10 Version 22H2 (OS Build 19045.6466)
    \end{itemize}


    \section{Benchmark Suite}
    \label{sec:benchmark-suite}

    The benchmark suite was designed to exercise common ECS operations individually,
    including sequential iteration, entity creation and destruction, sparse component access, and archetype transitions.
    By isolating these behaviors into separate scenarios, differences between implementations can be attributed
    to specific aspects of ECS execution.

    \subsection{Entity Iteration}
    \label{subsec:entity-iteration}

    This benchmark evaluated the performance of sequential entity iteration in the ECS framework.
    The goal was to isolate the performance of entity traversal and component access.
    Configurations specified the entity count ranging from 1,000 to 64,000 to compare the scalability of entity iteration.

    For this benchmark, we emulated the behavior of a 2-dimensional physics engine which adjusts an entity's position according to their velocity.
    We defined the components $\mathbf{Pos} \mapsto \mathbb{R}^2$
    and ${\mathbf{Vel} \mapsto \mathbb{R}^2}$.
    The system query was defined as $\mathrm{Q}_\mathrm{S} = \mathrm{Q}(\mathbf{Pos}, \mathbf{Vel})$.
    Lastly, the user system was defined as $\mathrm{S}(\Delta t) = \left[\forall e \in \mathrm{Q}_\mathrm{S} : e.\mathbf{Pos} \leftarrow e.\mathbf{Pos} + e.\mathbf{Vel} \Delta t\right]$.

    Before each configuration, the specified number of entities were created and initialized with
    $\mathbf{Pos} \in \left\{ [-100, 100]^2 \right\}$ and $\mathbf{Vel} \in \left\{[-10, 10]^2\right\}$.
    The distribution of the random initialization was uniform.

    \subsection{Sparse Access}
    \label{subsec:sparse-access}

    This benchmark evaluated the performance of systems querying sparse entity archetypes in the ECS framework.
    The ratio of entities of interest to total entities will be referred to as the sparse ratio $R_s$.
    By varying the sparse ratio, the query-forming efficiency of ECS frameworks under sparse scenarios could be compared.

    For this benchmark, we emulated the behavior of a system that interacts with only entities of interest.
    In this implementation, entities of interest rotate their positions around the origin.
    We used components $\mathbf{Pos} \mapsto \mathbb{R}^2$ and $\mathbf{Int} \mapsto \varnothing$.
    The system query was defined as $\mathrm{Q}_\mathrm{S} = Q(\mathbf{Pos}, \mathbf{Int})$.
    Lastly, the user system was defined as $\mathrm{S} = \left[\forall e \in \mathrm{Q}_\mathrm{S} : e.\mathbf{Pos} \leftarrow \mathrm{Rot}(e.\mathbf{Pos}) \right]$ where $\mathrm{Rot} : \mathbb{R}^2 \rightarrow \mathbb{R}^2, \quad (x,y) \mapsto (y,-x)$.

    Before each configuration, the set number of 32,000 entities was created and initialized with $\mathbf{Pos} \in \left\{ [-100, 100]^2 \right\}$.
    A random subset of the total entities with size $R_s \times \mathrm{Entity Count}$ were then attached with $\mathbf{Int}$ corresponding to the sparseness configuration.
    The distribution of the random initialization was uniform.

    \subsection{Entity Creation and Destruction}
    \label{subsec:entity-creation-and-destruction}

    This benchmark evaluated the performance of the ECS framework when creating and destroying entities while running user-defined systems.
    To maintain a steady state throughout the benchmark, we set entity creation and destruction to the same rate $E$.
    In this benchmark, we adjusted the entity rate between configurations on a range from 32 to 2048.

    For this benchmark, we emulated the behavior of a system that creates entities and removes them after their duration has expired.
    We defined components $\mathbf{Life} \mapsto \mathbb{Z}$ and the system query $\mathrm{Q}_\mathrm{S} = \mathrm{Q}(\mathbf{Life})$.
    The user systems are separated into the entity creation system $\mathrm{C} = \left[\varnothing : \text{spawn }E\text{ entities with }\mathbf{Life \mapsto 2} \right]$
    and the entity destruction system $\mathrm{D}$, which is defined as follows.

    \[
        \left[
            \forall e \in \mathrm{Q}_\mathrm{S} :
            \left.
                \begin{cases}
                    e.\mathbf{Life} \leftarrow e.\mathbf{Life} - 1 & \text{if }e.\mathbf{Life} > 1 \\
                    \text{destroy }e & \text{otherwise.}
                \end{cases}
            \right.
        \right]
        \tag{1}\label{eq:benchmark-3-entity-destruction-system}
    \]

    The configuration did not prepare entities on initialization of the setup.

    \subsection{Structural Changes}
    \label{subsec:structural-changes}

    This benchmark evaluated the performance of ECS frameworks under workloads requiring heavy structural changes.
    This included the adding and removing of components, the changing of entity archetypes, and the change in queried entities.
    While the number of components remained static, we vary the number of entities in the configuration on a range from 100 to 8000 entities to scale the workload.

    For this benchmark, we emulated a system that operated a binary counter.
    If the bit on the counter is set, the system would attach the corresponding component, and vice versa.
    We defined the number component $\mathbf{Num} \mapsto \mathbb{Z}$, the counter bit components $\mathbf{B}_i \mapsto \varnothing \text{ for } i \in \left\{ 0, 1, \dots, 7 \right\} $
    and the system query $\mathrm{Q}_\mathrm{S} = \mathrm{Q}(\mathbf{Num})$.

    The system for this benchmark is a more complex process.
    Let $\mathrm{O}_i$ and $\mathrm{P}_i$ be operations on an entity $e$.
    $\mathrm{O}_i$ will attach $\mathbf{B}_i$ to $e$ if $e$ did not have the component and the binary representation of $e.\mathbf{Num}$ is $1$ in its $i$th digit.
    $\mathrm{P}_i$ will detach $\mathbf{B}_i$ to $e$ if $e$ had the component and the binary representation of $e.\mathbf{Num}$ is $0$ in its $i$th digit.
    To put simply, $\mathrm{O}_i$ and $\mathrm{P}_i$ updates the component based on the entity's $\mathbf{Num}$ value.
    We can then define the system $\mathrm{S} = \left[\forall e \in \mathrm{Q}_\mathrm{S} : \text{Apply }\mathrm{O}_i(e), \mathrm{P}_i(e)\text{ for } i \in \left\{ 0, 1, \dots, 7 \right\} \right]$

    \paragraph*{Executable Size and Memory Usage}Table~\ref{tab:results-size-and-memory} shows the executable size and memory usage of the frameworks while running the workload according to the given scenarios.
    The size of the executable did not particularly change as each benchmark's configurations varied, while memory usage scaled linearly.
    As such, only one configuration of each scenario sufficed for display.
    We observe that the custom framework-built executable size was approximately 25\% the size of the equivalent EnTT-built executable (except for~\ref{subsec:structural-changes}, where it was around 16.1\%,) while the Bevy-built executable size is substantially higher.
    The simple explanation was that Bevy housed not just the ECS, but also various other features designed to support application development.
    Reducing Bevy from the overall engine to the parts relevant to the Bevy ECS would decrease executable size, but not by enough of a margin to contend with the other frameworks.

    Regarding memory usage, EnTT consumed the least memory, followed by the custom framework, then Bevy.
    As Bevy ECS is part of a broader engine ecosystem, the additional functionalities, such as change detection,
    scheduling infrastructure, metadata, and registries are likely to contribute to the larger memory footprint.
    Considering the other frameworks, the custom framework may have used more complex data storage
    and temporary objects compared to EnTT, such as the structured query objects, thereby contributing to more memory usage.

    \section{Discussion and Conclusion}
    \label{sec:conclusion}

    This paper investigated the extent to which compile-time specialization can improve the performance of ECS implementations.
    A custom C++ ECS was developed using compile-time component storage, query construction, and system registration,
    and evaluated for performance against EnTT and Bevy with reference to synthesized ECS workloads.
    The results did not demonstrate a universal performance advantage but showed that extensive compile-time specialization
    can produce competitive performance for several ECS workloads.

    The custom implementation performed particularly well for entity iteration and remained competitive for entity
    creation and destruction, but performed worse for sparse access.
    This suggests that compile-time specialization can reduce overhead in type-dependent ECS operations
    but cannot compensate for either the underlying costs of the storage architecture or the efficiency of the implementation details.
    In particular, the sparse-set design provided efficient structural modification while limiting performance
    for workloads dominated by sparse component access.
    Bevy's performance at higher entity counts also demonstrates the advantage that
    archetype storage can provide for dense iteration.

    The custom implementation also produced substantially smaller executables than the evaluated frameworks,
    although the comparison with Bevy is not directly equivalent because Bevy provides broader engine functionality.
    Runtime memory usage, however, was higher than EnTT in the evaluated scenarios.
    These results indicate that reducing runtime infrastructure through compile-time specialization
    does not necessarily reduce all aspects of the resource footprint.

    Overall, the results suggest that extensive compile-time specialization can produce performance competitive
    with established ECS frameworks, particularly for predictable iteration and structural workloads.
    However, its effectiveness depends on the underlying storage architecture and access patterns.
    Compile-time specialization should therefore be considered as one part of ECS performance design,
    rather than a replacement for appropriate storage and execution strategies outright, for maximal benefits.

    \section{Limitations}
    \label{sec:limitations}

    Bevy is written in Rust while the other implementations are in C++, so compiler and language differences may affect the measured performance.
    The C++ implementations were compiled with Clang to use the same LLVM backend as Rust,
    but the results should still be interpreted as comparisons between complete framework implementations rather than compiler-independent measurements.
    All benchmarks were also run on a single hardware configuration, so hardware-specific effects cannot be excluded.

    The workloads were designed to isolate specific ECS operations rather than represent complete applications,
    so the results may not generalize to workloads with many interacting systems or different access patterns.
    Randomized entity creation and limited repetitions may also additionally introduce measurement variance.

    The evaluated configurations also do not necessarily represent the maximum performance of each framework.
    EnTT was tested using standard views rather than owned groups, and the Bevy configuration
    used minimal plugins without evaluating additional mechanisms such as conditional system execution or events.
    Results therefore reflect the tested configurations rather than the maximum achievable performance of each framework.
